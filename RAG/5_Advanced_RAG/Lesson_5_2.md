# Lesson 5.2 — Self-RAG: Selective Retrieval and Reflection Tokens

---

## The Core Insight Behind Self-RAG

Standard RAG retrieves on every query, without exception. A user asks "what is 2 + 2?" — retrieval runs anyway. A user asks a complex question about a topic not in your corpus — retrieval runs, returns irrelevant chunks, and the LLM either hallucinates or gives a confused answer.

This is wasteful in two directions:
- **Over-retrieval:** Retrieval for queries that do not need it (simple factual, conversational, mathematical) adds latency and can actually hurt answer quality by introducing irrelevant context.
- **Under-detection:** When retrieval fails, the system does not know — it proceeds to generation with bad context.

Self-RAG (Asai et al., 2023) proposes a fundamentally different model: the LLM itself decides whether retrieval is needed, assesses the quality of retrieved content, and critiques its own output — all within a single generation pass using special tokens called reflection tokens.

The key distinction from CRAG: CRAG uses a separate evaluator model after retrieval. Self-RAG embeds the evaluation capability inside the generation model itself, as part of its output.

---

## Reflection Tokens: The Mechanism

Self-RAG works by training a language model to generate four types of special tokens interspersed with its regular output:

**[Retrieve]** — Should retrieval happen for this generation?
- `[Retrieve=Yes]` — Retrieve documents before continuing.
- `[Retrieve=No]` — Generate from parametric knowledge without retrieval.

**[ISREL]** — Is the retrieved passage relevant to the query?
- `[ISREL=relevant]` — This passage is relevant, use it.
- `[ISREL=irrelevant]` — This passage is not relevant, ignore it.

**[ISSUP]** — Does the generated segment use the retrieved content faithfully?
- `[ISSUP=fully supported]` — Every claim in the generated segment is supported by the passage.
- `[ISSUP=partially supported]` — Some claims are supported, some are not.
- `[ISSUP=no support]` — The generated segment is not supported by the retrieved passage.

**[ISUSE]** — Is this generated segment useful for the user's request?
- `[ISUSE=5]` down to `[ISUSE=1]` — Usefulness score 1–5.

A Self-RAG generation looks like:

```
User: What are the symptoms of appendicitis?

Model generates:
[Retrieve=Yes]
[Retrieved passage: "Appendicitis is characterized by..."]
[ISREL=relevant]
The main symptoms of appendicitis include [ISSUP=fully supported] pain beginning around the navel that moves to the lower right abdomen, nausea, vomiting, and fever. [ISSUP=fully supported] The pain typically worsens over 12-24 hours.
[ISUSE=5]
```

The model decides to retrieve, assesses the retrieved passage as relevant, generates content that is fully supported by the passage, and judges the output as highly useful — all within one generation sequence.

---

## How Self-RAG Is Trained

Self-RAG requires a specifically trained model — you cannot take an existing LLM and add Self-RAG behavior through prompting alone. The training process has two stages:

### Stage 1 — Critic Model Training

Train a separate "critic" model (typically a smaller LLM) to generate reflection token annotations for (query, passage, generation) triples.

```
Training data creation:
  For each (query, retrieved_passages, generated_response) triple:
  - Annotate: should retrieval have been done? → [Retrieve] label
  - Annotate: is each passage relevant? → [ISREL] label
  - Annotate: is each sentence supported? → [ISSUP] label
  - Annotate: is the response useful? → [ISUSE] label
  
  This creates a dataset of annotated (query, response) pairs.
```

The reflection token labels are generated by a powerful LLM (like GPT-4) used as the annotator, then used to fine-tune a smaller critic model.

### Stage 2 — Generator Model Training

Fine-tune the main generator model on the annotated corpus. The training objective is standard next-token prediction, but the training sequences contain interleaved reflection tokens and regular text:

```
Training sequence:
  "Query: ... [Retrieve=Yes] [passage text] [ISREL=relevant] Response text [ISSUP=fully supported] [ISUSE=5]"
```

The generator learns to produce reflection tokens naturally as part of its output — they become part of its vocabulary and generation behavior.

## Approximating Self-RAG Without a Fine-Tuned Model

Training a full Self-RAG model is expensive and requires specialized infrastructure. For most teams, a practical approximation using prompt engineering captures most of the value.

### Approximation 1 — Retrieval Necessity Classifier

Before running retrieval, classify whether the query needs retrieval at all.

```python
async def should_retrieve(
    query: str,
    conversation_history: list[dict],
    llm_client
) -> dict:
    """
    Classify whether retrieval is needed for this query.
    Approximates the [Retrieve] reflection token.
    """
    
    system_prompt = """Classify whether the following question requires retrieving 
information from documents to answer correctly.

Retrieval IS needed when:
- The question is about specific facts, policies, procedures, or data
- The answer depends on information that may have changed or is domain-specific
- The question asks about internal documents, contracts, regulations, or guidelines

Retrieval is NOT needed when:
- The question can be answered from general knowledge (e.g., "what is Python?")
- The question is conversational or social (e.g., "thank you!", "that makes sense")
- The question asks about something just stated in the conversation
- The question is mathematical or logical and requires no external information

Respond with JSON:
{
    "needs_retrieval": true/false,
    "reason": "brief explanation",
    "retrieval_query": "optimized query for retrieval if needs_retrieval is true, else null"
}"""
    
    recent_history = conversation_history[-4:] if conversation_history else []
    history_text = "\n".join([
        f"{t['role'].upper()}: {t['content'][:200]}" 
        for t in recent_history
    ])
    
    response = await llm_client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": f"Conversation:\n{history_text}\n\nNew question: {query}"}
        ],
        response_format={"type": "json_object"},
        max_tokens=150,
        temperature=0.0
    )
    
    import json
    return json.loads(response.choices[0].message.content)
```

### Approximation 2 — Per-Passage Relevance Scoring

After retrieval, assess whether each retrieved passage is relevant before passing it to generation. Approximates [ISREL].

```python
async def score_passage_relevance(
    query: str,
    passages: list[dict],
    llm_client,
    text_key: str = "text"
) -> list[dict]:
    """
    Score each retrieved passage for relevance.
    Approximates the [ISREL] reflection token.
    Returns passages with relevance scores, filtering out irrelevant ones.
    """
    
    async def score_one(passage: dict) -> dict:
        prompt = f"""Rate the relevance of this passage to the question.

Question: {query}
Passage: {passage[text_key][:800]}

Respond with JSON:
{{
    "relevance": "relevant" | "partially_relevant" | "irrelevant",
    "score": 0-10,
    "reason": "one sentence explanation"
}}"""
        
        response = await llm_client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}],
            response_format={"type": "json_object"},
            max_tokens=100,
            temperature=0.0
        )
        
        import json
        scoring = json.loads(response.choices[0].message.content)
        return {**passage, "isrel_score": scoring["score"], "isrel": scoring["relevance"]}
    
    # Score all passages in parallel
    scored = await asyncio.gather(*[score_one(p) for p in passages])
    
    # Filter to relevant and partially relevant only
    relevant = [p for p in scored if p["isrel"] != "irrelevant"]
    
    return sorted(relevant, key=lambda x: x["isrel_score"], reverse=True)
```

### Approximation 3 — Post-Generation Support Check

After generating the response, check whether each claim is supported by the retrieved passages. Approximates [ISSUP].

```python
async def check_generation_support(
    query: str,
    passages: list[dict],
    generated_response: str,
    llm_client,
    text_key: str = "text"
) -> dict:
    """
    Check whether the generated response is supported by retrieved passages.
    Approximates the [ISSUP] reflection token.
    """
    
    passages_text = "\n\n".join([
        f"Passage {i+1}: {p[text_key][:600]}"
        for i, p in enumerate(passages)
    ])
    
    prompt = f"""Check whether the following response is supported by the provided passages.

Question: {query}

Passages:
{passages_text}

Generated response:
{generated_response}

For each claim in the response, determine if it is:
- fully_supported: directly stated in the passages
- partially_supported: partially in the passages or inferable
- not_supported: not in the passages (may be hallucinated)

Respond with JSON:
{{
    "overall_support": "fully_supported" | "partially_supported" | "not_supported",
    "support_score": 0.0-1.0,
    "unsupported_claims": ["list of claims not supported by passages"],
    "issup": "fully supported" | "partially supported" | "no support"
}}"""
    
    response = await llm_client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
        response_format={"type": "json_object"},
        max_tokens=400,
        temperature=0.0
    )
    
    import json
    return json.loads(response.choices[0].message.content)
```

### Approximation 4 — Usefulness Assessment

After generation, assess whether the response actually answers the user's question. Approximates [ISUSE].

```python
async def assess_usefulness(
    query: str,
    response: str,
    llm_client
) -> dict:
    """
    Assess whether the generated response is useful.
    Approximates the [ISUSE] reflection token.
    """
    
    prompt = f"""Rate how useful this response is for answering the question.

Question: {query}

Response: {response}

Score from 1-5:
5 = Completely answers the question with no gaps
4 = Mostly answers the question with minor gaps
3 = Partially answers the question
2 = Minimally helpful, major gaps
1 = Does not answer the question

Respond with JSON: {{"isuse_score": 1-5, "reasoning": "brief explanation"}}"""
    
    result = await llm_client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}],
        response_format={"type": "json_object"},
        max_tokens=100,
        temperature=0.0
    )
    
    import json
    return json.loads(result.choices[0].message.content)
```

## The Complete Approximate Self-RAG Pipeline

Combining all four approximations into a coherent pipeline:

```python
class ApproximateSelfRAG:
    def __init__(
        self,
        retriever,
        llm_client,
        min_usefulness_score: int = 3,
        min_support_score: float = 0.7,
        max_retrieval_attempts: int = 2
    ):
        self.retriever = retriever
        self.llm = llm_client
        self.min_usefulness = min_usefulness_score
        self.min_support = min_support_score
        self.max_attempts = max_retrieval_attempts
    
    async def answer(
        self,
        query: str,
        conversation_history: list[dict] = None
    ) -> dict:
        """
        Approximate Self-RAG pipeline.
        """
        
        if conversation_history is None:
            conversation_history = []
        
        # Step 1: Decide whether retrieval is needed [Retrieve]
        retrieval_decision = await should_retrieve(
            query, conversation_history, self.llm
        )
        
        if not retrieval_decision["needs_retrieval"]:
            # Generate directly from parametric knowledge
            response = await self._generate_without_context(query)
            return {
                "answer": response,
                "retrieved": False,
                "reason": retrieval_decision["reason"]
            }
        
        # Use the optimized retrieval query if provided
        retrieval_query = retrieval_decision.get("retrieval_query", query)
        
        # Step 2: Retrieve
        raw_results = await self.retriever.retrieve(retrieval_query)
        
        # Step 3: Score passage relevance [ISREL]
        relevant_results = await score_passage_relevance(
            query, raw_results, self.llm
        )
        
        if not relevant_results:
            # All passages irrelevant — escalate
            return {
                "answer": "I couldn't find relevant information to answer this question.",
                "retrieved": True,
                "isrel": "all_irrelevant",
                "escalate": True
            }
        
        # Step 4: Generate response
        context = format_context(relevant_results)
        generated = await self._generate_with_context(query, context)
        
        # Step 5: Check support [ISSUP]
        support_check = await check_generation_support(
            query, relevant_results, generated, self.llm
        )
        
        # Step 6: Check usefulness [ISUSE]
        usefulness = await assess_usefulness(query, generated, self.llm)
        
        # Step 7: Decide whether to retry or accept
        if (support_check["support_score"] >= self.min_support and 
            usefulness["isuse_score"] >= self.min_usefulness):
            return {
                "answer": generated,
                "retrieved": True,
                "issup": support_check["issup"],
                "isuse": usefulness["isuse_score"],
                "support_score": support_check["support_score"]
            }
        
        # Low support or usefulness — try to improve
        if support_check["issup"] == "not_supported":
            # Generation went beyond context — regenerate with stronger grounding
            generated = await self._generate_with_stricter_grounding(
                query, context, support_check["unsupported_claims"]
            )
            return {
                "answer": generated,
                "retrieved": True,
                "regenerated": True,
                "reason": "low_support"
            }
        
        # Accept with low usefulness flag
        return {
            "answer": generated,
            "retrieved": True,
            "low_usefulness_warning": usefulness["isuse_score"] < self.min_usefulness,
            "isuse": usefulness["isuse_score"]
        }
    
    async def _generate_without_context(self, query: str) -> str:
        response = await self.llm.chat.completions.create(
            model="gpt-4o",
            messages=[
                {"role": "system", "content": "Answer the question directly and concisely."},
                {"role": "user", "content": query}
            ],
            max_tokens=500,
            temperature=0.1
        )
        return response.choices[0].message.content
    
    async def _generate_with_context(self, query: str, context: str) -> str:
        response = await self.llm.chat.completions.create(
            model="gpt-4o",
            messages=[
                {"role": "system", "content": "Answer using only the provided context."},
                {"role": "user", "content": f"Context:\n{context}\n\nQuestion: {query}"}
            ],
            max_tokens=800,
            temperature=0.1
        )
        return response.choices[0].message.content
    
    async def _generate_with_stricter_grounding(
        self, query: str, context: str, unsupported_claims: list[str]
    ) -> str:
        prompt = f"""Context:\n{context}\n\nQuestion: {query}

IMPORTANT: Your previous response included these claims that are NOT in the context:
{unsupported_claims}

Generate a new response using ONLY information from the provided context.
Do not include the above claims unless they appear in the context."""
        
        response = await self.llm.chat.completions.create(
            model="gpt-4o",
            messages=[
                {"role": "system", "content": "Answer using only the provided context."},
                {"role": "user", "content": prompt}
            ],
            max_tokens=800,
            temperature=0.0
        )
        return response.choices[0].message.content
```

## Beam Search Over Reflection Token Sequences

In the original Self-RAG paper, the model generates multiple candidate responses in parallel (beam search) using different retrieved passages. Each beam is scored using the reflection token probabilities, and the highest-scoring beam is selected as the final answer.

```python
async def self_rag_beam_search(
    query: str,
    retriever,
    llm_client,
    n_beams: int = 3,
    n_passages_per_beam: int = 1
) -> dict:
    """
    Approximate beam search over retrieved passages.
    Generate one response per passage, select best by support score.
    """
    
    # Retrieve n_beams * n_passages_per_beam candidates
    all_results = await retriever.retrieve(query, k=n_beams * n_passages_per_beam)
    
    # Score relevance for all
    relevant = await score_passage_relevance(query, all_results, llm_client)
    
    if not relevant:
        return {"answer": "No relevant information found.", "beam_selected": -1}
    
    # Generate one response per top passage (beam)
    top_passages = relevant[:n_beams]
    
    beam_tasks = [
        _generate_with_single_passage(query, passage, llm_client)
        for passage in top_passages
    ]
    beam_responses = await asyncio.gather(*beam_tasks)
    
    # Score each beam by support
    support_tasks = [
        check_generation_support(query, [passage], response, llm_client)
        for passage, response in zip(top_passages, beam_responses)
    ]
    support_scores = await asyncio.gather(*support_tasks)
    
    # Select beam with highest support score
    best_idx = max(
        range(len(support_scores)),
        key=lambda i: support_scores[i]["support_score"]
    )
    
    return {
        "answer": beam_responses[best_idx],
        "beam_selected": best_idx,
        "support_score": support_scores[best_idx]["support_score"],
        "all_beam_scores": [s["support_score"] for s in support_scores]
    }


async def _generate_with_single_passage(
    query: str, passage: dict, llm_client
) -> str:
    response = await llm_client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": "Answer using only the provided passage."},
            {"role": "user", "content": f"Passage:\n{passage['text']}\n\nQuestion: {query}"}
        ],
        max_tokens=500,
        temperature=0.1
    )
    return response.choices[0].message.content
```

Beam search over passages is useful when multiple retrieved passages have different but complementary information about the query. The beam with the best support score is the answer most grounded in actual retrieved content.

## Latency and Cost of Approximate Self-RAG

The approximation involves multiple LLM calls. Let us count them for a typical query that needs retrieval:

| Step | Model | Estimated latency |
|---|---|---|
| Retrieval necessity check | gpt-4o-mini | ~100ms |
| Retrieval (hybrid search) | — | ~50ms |
| Passage relevance scoring (5 passages, parallel) | gpt-4o-mini | ~200ms |
| Generation | gpt-4o | ~500ms |
| Support check | gpt-4o | ~300ms |
| Usefulness check | gpt-4o-mini | ~100ms |
| **Total** | | **~1.25s** |

This is roughly 2× the latency of standard RAG. For most production systems targeting 2–3s total response time, this is acceptable. For latency-critical applications (< 1s), full approximate Self-RAG is too expensive.

**Selective application:** Apply full Self-RAG only for queries above a complexity threshold or for domains where quality requirements are highest. Use standard RAG for simple factual lookups.

## Self-RAG vs. CRAG: When to Use Which

| | Self-RAG | CRAG |
|---|---|---|
| **Primary capability** | Decides whether to retrieve at all | Evaluates and corrects retrieval quality |
| **Requires fine-tuning** | Yes (full version), No (approximation) | No |
| **Fallback strategy** | Skip retrieval or re-retrieve | Web search or IDK |
| **Best for** | Reducing unnecessary retrieval, mixed-need query streams | Incomplete corpus, known external knowledge needs |
| **Multiple passage evaluation** | Yes (per-passage [ISREL]) | Holistic quality score |
| **Output critique** | Yes ([ISSUP], [ISUSE]) | No (only retrieval evaluated) |

They are complementary rather than competing. A system can use Self-RAG's retrieval necessity classification with CRAG's web search fallback — the best architectural combination for systems with incomplete corpora and mixed query types.

---

## Summary

- Self-RAG embeds retrieval decision-making and output quality assessment inside the LLM using special reflection tokens: [Retrieve], [ISREL], [ISSUP], [ISUSE].
- Full Self-RAG requires a fine-tuned model trained to generate reflection tokens. This is expensive and requires significant infrastructure.
- Approximate Self-RAG implements each reflection token as a separate LLM call: retrieval necessity classifier, per-passage relevance scorer, support checker, and usefulness assessor.
- Beam search over retrieved passages selects the response most grounded in the retrieved content by comparing support scores across multiple generation candidates.
- Approximate Self-RAG adds ~2× latency over standard RAG. Apply selectively based on query complexity or domain stakes.
- Self-RAG addresses unnecessary retrieval and output quality. CRAG addresses corpus incompleteness and external fallback. They complement each other.
